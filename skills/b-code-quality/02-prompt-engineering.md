## 提示词工程概述

### 什么是提示词工程？

**定义**：提示词工程是设计和优化与 Claude Code 沟通的提示词，以获得最佳结果的技术和艺术。

```
差的提示词：
"创建一个登录组件"

好的提示词：
"创建一个React登录组件，使用TypeScript，
包含邮箱和密码输入、表单验证、错误提示，
集成到现有的AuthContext，遵循项目的TailwindCSS样式"
```

### 为什么重要？

#### 1. 效率提升

```
好的提示词 → 一次生成可用代码
差的提示词 → 多次迭代修改

效率差异：3-5倍
```

#### 2. 质量提升

```
明确的提示词 → 符合预期的代码
模糊的提示词 → 需要大幅修改
```

#### 3. 成本优化

```
一次好的提示词 < 多次差的提示词

Token 成本节省：50-70%
```

#### 4. 体验提升

```
好的沟通 → 愉快的协作
差的沟通 → 挫折和反复
```

## 核心原则

### 原则 1: 具体明确 (Be Specific)

#### ❌ 模糊的提示词

```
"优化这个函数"
"修复这个bug"
"创建一个组件"
```

#### ✅ 具体的提示词

```
"优化 dataProcessor.ts 中的 process 函数，
使用 Map 替代数组查找以提高性能，
目标是将处理时间从 500ms 降低到 100ms 以下"

"修复用户登录时出现的 500 错误，
错误出现在 AuthController.js 的 login 方法中，
错误信息是 'Cannot read property \"token\" of undefined'"

"创建一个 React 表单组件，用于用户注册，
包含：用户名、邮箱、密码、确认密码四个字段，
使用 TypeScript 定义 Props，
使用 TailwindCSS 样式化，
集成 react-hook-form 进行表单管理"
```

### 原则 2: 提供上下文 (Provide Context)

#### ❌ 缺少上下文

```
"添加错误处理"
```

#### ✅ 提供上下文

```
"@src/services/api.ts 为所有 fetch 函数添加错误处理，
当服务器返回 4xx 或 5xx 状态码时，
抛出包含错误消息和状态码的异常，
使用项目的 ApiError 类（定义在 @src/utils/errors.ts）"
```

### 原则 3: 明确输出 (Specify Output)

#### ❌ 不明确输出

```
"分析这个代码"
```

#### ✅ 明确输出

```
"分析 @src/components/UserProfile.tsx，
请提供：
1. 组件的功能概述（2-3句话）
2. Props 类型定义
3. 使用的 Hooks
4. 潜在的性能问题（如果有）
5. 改进建议（如果有）

以 Markdown 列表格式输出"
```

### 原则 4: 迭代优化 (Iterate)

```
第一次提示词：
"创建用户认证系统"
→ 结果：基础功能

第二次提示词：
"添加记住密码功能"
→ 结果：扩展功能

第三次提示词：
"添加双因素认证"
→ 结果：更完善

比一次性要求所有功能更有效
```

### 原则 5: 使用示例 (Use Examples)

#### ❌ 没有示例

```
"遵循项目的代码风格"
```

#### ✅ 提供示例

```
"创建产品列表组件，遵循项目的代码风格，
参考 @src/components/UserList.tsx 的结构：

- 使用函数式组件
- Props 使用 interface 定义
- 使用 useMemo 优化列表渲染
- 使用 TailwindCSS 类名
- 组件文件命名为 .tsx

创建 ProductList 组件，包含产品名称、价格、库存状态"
```

## 提示词结构

### 完整的提示词结构

```markdown
1. **角色/上下文**（可选）
   "你是一个React专家..."

2. **任务描述**（必需）
   "创建一个..."

3. **具体要求**（必需）
   - 功能要求
   - 技术要求
   - 约束条件

4. **输入数据**（如果适用）
   "@file.ts"
   "使用这个数据..."

5. **输出格式**（推荐）
   "请提供..."
   "以...格式输出"

6. **示例/参考**（推荐）
   "参考..."
   "类似..."

7. **验证标准**（可选）
   "确保..."
   "验证..."
```

### 结构示例

#### 示例 1: 创建组件

```
【任务】
创建一个 React 数据表格组件

【具体要求】
- 支持排序（点击列标题）
- 支持分页（每页10条）
- 支持筛选（搜索框）
- 使用 TypeScript
- 集成到现有的 @src/components/Table.tsx

【样式】
- 使用 TailwindCSS
- 参考项目中的 @src/components/UserList.tsx

【数据格式】
```typescript
interface Column {
  key: string;
  label: string;
  sortable?: boolean;
}

interface DataTableProps {
  columns: Column[];
  data: Record<string, any>[];
}
```

【功能】
1. 点击列标题排序
2. 底部显示分页控件
3. 顶部显示搜索框
4. 空数据时显示提示

请创建完整的组件，包括 TypeScript 类型定义。
```

#### 示例 2: 重构代码

```
【任务】
重构 @src/utils/dataProcessor.ts 中的 process 函数

【当前问题】
- 函数有 200 行，难以维护
- 包含重复的验证逻辑
- 缺少错误处理
- 性能问题（使用嵌套循环）

【重构目标】
1. 拆分为多个小函数（单一职责）
2. 提取验证逻辑到独立函数
3. 添加 try-catch 错误处理
4. 使用 Map 优化查找性能

【约束条件】
- 不改变函数的外部接口
- 保持向后兼容
- 添加单元测试

【验证】
重构后：
- 函数长度 < 50 行
- 所有测试通过
- 性能提升 50% 以上

请先分析当前代码，然后提供重构方案。
```

#### 示例 3: 修复 Bug

```
【任务】
修复用户登录时的 500 错误

【错误信息】
```
Error: Cannot read property "token" of undefined
    at AuthController.login (src/controllers/AuthController.ts:45:15)
```

【相关文件】
@src/controllers/AuthController.ts
@src/services/AuthService.ts
@src/models/User.ts

【场景】
用户使用邮箱和密码登录
当密码正确时，应该返回 JWT token
但当前代码在访问 user.token 时报错

【要求】
1. 分析错误原因
2. 修复 bug
3. 添加错误处理
4. 添加测试用例防止回归

【期望结果】
- 登录成功返回 token
- 登录失败返回明确的错误消息
- 不会抛出未捕获的异常
```

## 反模式识别

### 反模式 1: 过于宽泛

```
❌ 反模式：
"帮我写代码"
"优化性能"
"修复bug"

✅ 正确做法：
明确具体的任务和期望
```

### 反模式 2: 假设理解

```
❌ 反模式：
"修改这个文件"（假设Claude知道你要怎么改）

✅ 正确做法：
"修改 @src/config.ts，
将 API_BASE_URL 从 'http://localhost:3000'
改为 'https://api.example.com'"
```

### 反模式 3: 缺少上下文

```
❌ 反模式：
"添加验证"
（什么验证？验证什么？）

✅ 正确做法：
"为注册表单添加验证：
- 用户名：3-20字符，字母数字
- 邮箱：有效的邮箱格式
- 密码：至少8字符，包含大小写字母和数字
使用 HTML5 验证 + JavaScript 验证"
```

### 反模式 4: 矛盾的要求

```
❌ 反模式：
"创建一个简单的登录页面，
但要包含：
- 社交登录
- 双因素认证
- 忘记密码
- 注册功能"

（简单 vs 复杂矛盾）

✅ 正确做法：
优先级排序，分阶段实现
```

### 反模式 5: 一次性要求太多

```
❌ 反模式：
"创建一个完整的ERP系统，包含：
- 财务模块
- 库存模块
- 销售模块
- 人力资源
- 客户关系管理"

✅ 正确做法：
先从一个模块开始，逐步构建
```

### 反模式 6: 忽略代码风格

```
❌ 反模式：
不说明代码风格规范

✅ 正确做法：
"遵循项目的代码规范：
- 使用 ESLint + Prettier
- 组件命名 PascalCase
- 函数命名 camelCase
- 参考 @src/components/Button.tsx"
```

### 反模式 7: 不说明技术栈

```
❌ 反模式：
"创建后端API"

✅ 正确做法：
"使用 Node.js + Express + TypeScript 创建 REST API，
遵循项目现有的架构（参考 @src/routes/）"
```
