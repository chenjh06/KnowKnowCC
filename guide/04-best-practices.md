## 思维模式错误

### 错误 1: 把 Claude Code 当搜索引擎 ❌

#### 症状

```
👤 你：Python 列表推导式怎么写？

👤 你：React useEffect 依赖数组怎么用？

👤 你：Git rebase 怎么操作？
```

#### 问题分析

**Claude Code ≠ 搜索引擎**

| 搜索引擎 | Claude Code |
|---------|-------------|
| 查找信息 | 执行任务 |
| 快速答案 | 深度理解 |
| 被动接收 | 主动协作 |
| 一次性 | 持续对话 |

**正确用法**：

```
❌ 错误：
"Python 列表推导式怎么写？"
（可以直接搜索的问题）

✅ 正确：
"帮我用列表推导式重构这个函数，提高性能"
[引用代码文件]
（需要理解上下文的任务）
```

#### 何时使用搜索引擎

```
✅ 使用搜索引擎：
- 查询 API 文档
- 查找错误代码含义
- 快速语法查询
- 查看库的版本

✅ 使用 Claude Code：
- 代码重构
- Bug 修复
- 架构设计
- 功能实现
```

#### 实战对比

**场景**：需要实现一个防抖函数

```
❌ 错误做法：
👤 你：JavaScript 防抖函数怎么写？

🤖 Claude：[给出通用代码]

👤 你：[复制、粘贴、修改以适配项目]

✅ 正确做法：
👤 你：@src/utils/debounce.js 为这个文件添加防抖功能，
        集成到现有的工具函数体系中

🤖 Claude：
[读取现有代码]
[理解项目结构]
[添加符合项目风格的防抖函数]
[更新相关导入]
```

### 错误 2: 期待完美代码 ❌

#### 症状

```
👤 你：创建一个用户认证系统
🤖 Claude：[生成代码]
👤 你：[直接使用，没有审查]
💥 生产环境出现安全漏洞
```

#### 问题分析

**Claude Code 的限制**：

1. **可能产生的错误**：
   - 逻辑漏洞
   - 边界情况未处理
   - 性能问题
   - 安全漏洞

2. **无法替代人类**：
   - 业务理解
   - 架构决策
   - 安全审查
   - 用户体验

#### 正确心态

```
Claude Code = 助手，不是替代品

┌─────────────────────────────────────┐
│  Claude Code 的角色                  │
│  └─ 生成初步代码                     │
│  └─ 提供实现思路                     │
│  └─ 处理重复性工作                   │
│                                      │
│  你的角色                            │
│  └─ 理解业务需求                     │
│  └─ 审查代码质量                     │
│  └─ 测试和验证                       │
│  └─ 最终决策和责任                   │
└─────────────────────────────────────┘
```

#### 审查检查清单

每次 Claude Code 生成代码后，必须检查：

```markdown
## 功能检查
- [ ] 代码实现了所有需求？
- [ ] 边界情况已处理？
- [ ] 错误处理完善？

## 质量检查
- [ ] 代码可读性好？
- [ ] 遵循项目规范？
- [ ] 命名清晰明确？

## 安全检查
- [ ] 输入验证？
- [ ] 敏感信息保护？
- [ ] 权限检查？

## 性能检查
- [ ] 没有明显性能问题？
- [ ] 资源使用合理？
- [ ] 可扩展性考虑？
```

#### 实战案例

**场景**：创建用户注册功能

```
❌ 不审查：
👤 你：创建用户注册 API
🤖 Claude：[生成代码]
👤 你：[直接部署]
💥 SQL 注入漏洞

✅ 审查后使用：
👤 你：创建用户注册 API，包含输入验证和防 SQL 注入
🤖 Claude：[生成带保护的代码]
👤 你：
    [审查代码]
    [测试各种输入]
    [检查安全性]
    [确认无误后使用]
```

### 错误 3: 缺乏审查意识 ❌

#### 症状

```
👤 你：重构这个函数
🤖 Claude：[修改代码]
👤 你：[按 Ctrl+S 保存]
💥 破坏了现有功能
```

#### 问题分析

**为什么需要审查？**

```
Claude Code 生成代码
    ↓
可能的问题：
├─ 逻辑错误（10%）
├─ 类型错误（15%）
├─ 边界情况遗漏（20%）
├─ 性能问题（10%）
└─ 与现有代码冲突（5%）
    ↓
需要人工审查
```

#### 三级审查法

**Level 1: 快速扫描（30秒）**

```markdown
- [ ] 代码语法正确？
- [ ] 没有明显的错误？
- [ ] 符合预期结构？
```

**Level 2: 功能审查（2分钟）**

```markdown
- [ ] 实现了所有需求？
- [ ] 错误处理完善？
- [ ] 边界情况考虑？
- [ ] 测试覆盖主要场景？
```

**Level 3: 深度审查（5-10分钟）**

```markdown
- [ ] 代码可读性和维护性？
- [ ] 性能和安全性？
- [ ] 与现有代码一致？
- [ ] 遵循最佳实践？
```

#### 审查技巧

**技巧 1: 对比修改**

```bash
# 使用 Git 查看修改
!git diff

# 或要求 Claude 解释变更
"解释你做的修改"
```

**技巧 2: 测试验证**

```bash
# 运行测试
!npm test

# 手动测试关键功能
```

**技巧 3: 代码审查工具**

```bash
# 使用 ESLint
!npm run lint

# 使用 TypeScript 检查
!npx tsc --noEmit
```

#### 实战案例

**场景**：Claude 修改了复杂函数

```
❌ 不审查：
🤖 Claude：[修改函数]
👤 你：[保存]
💥 引入 bug

✅ 审查：
🤖 Claude：[修改函数]

👤 你：
    [Level 1: 快速扫描]
    ✓ 语法正确

    [Level 2: 功能审查]
    ❓ "为什么删除了这个错误处理？"
    🤖 Claude：解释原因
    👤 你：确认合理性

    [Level 3: 深度审查]
    ✓ 性能无影响
    ✓ 代码更清晰

    [运行测试]
    !npm test
    ✓ 测试通过

    [保存]
```

## 使用方法错误

### 错误 4: 指令过于模糊 ❌

#### 症状

```
❌ 过于模糊：
"优化这个代码"
"修复这个 bug"
"改进这个函数"

结果：Claude 猜测你的意图，可能不符合需求
```

#### 问题分析

**Claude Code 不是读心术师**

```
模糊指令
    ↓
Claude 猜测
    ↓
可能的方向：
├─ 性能优化？
├─ 可读性改进？
├─ 安全增强？
├─ 功能扩展？
└─ Bug 修复？
    ↓
不确定的结果
```

#### 明确指令的 5W1H

**What（做什么）**
```
❌ 优化代码
✅ 重构这个函数，应用单一职责原则
```

**Why（为什么）**
```
✅ 重构这个函数，因为它有 200 行，难以维护
```

**Where（在哪里）**
```
✅ 重构 src/utils/dataProcessor.ts 中的 process 函数
```

**When（何时）**
```
✅ 在完成新功能后重构，不要现在
```

**Who（谁/范围）**
```
✅ 只重构 process 函数，不改动其他文件
```

**How（怎么做）**
```
✅ 将 process 函数拆分为 3 个子函数
```

#### 实战对比

**场景**：处理一个慢查询

```
❌ 模糊：
👤 你：优化这个查询函数

🤖 Claude：
[可能优化：索引、缓存、算法、数据结构...]
[不确定哪个方向]

✅ 明确：
👤 你：@src/db/queries.ts 的 getUserOrders 函数太慢，
    目前需要 3 秒，请通过添加数据库索引优化到 500ms 以内

🤖 Claude：
[明确目标：500ms]
[明确方法：添加索引]
[具体位置：getUserOrders]
[生成精准方案]
```

#### SMART 原则

```
S - Specific（具体的）
   ✅ 为 React 组件添加错误边界
   ❌ 改进组件

M - Measurable（可衡量的）
   ✅ 减少加载时间到 2 秒以内
   ❌ 提高性能

A - Achievable（可实现的）
   ✅ 添加单元测试覆盖主要功能
   ❌ 测试所有情况（可能不现实）

R - Relevant（相关的）
   ✅ 重构登录函数以支持新需求
   ❌ 重构整个项目

T - Time-bound（有时限的）
   ✅ 今天完成用户认证功能
   ❌ 尽快完成
```

### 错误 5: 一次性要求太多 ❌

#### 症状

```
❌ 一次性要求太多：
👤 你：创建一个完整的电商系统，包括：
    - 用户认证
    - 商品管理
    - 购物车
    - 订单处理
    - 支付集成
    - 库存管理
    - 物流跟踪
    - 数据分析
    - 后台管理

结果：
- Claude 可能遗漏部分需求
- 代码质量下降
- 难以审查
- 出错难以定位
```

#### 问题分析

**认知负荷理论**

```
一次性任务数量
    ↓
1-3 个   → ✅ 高质量，易审查
4-7 个   → ⚠️ 中等质量，需仔细审查
8+ 个    → ❌ 质量下降，错误增多
```

#### 分步执行策略

**策略 1: MVP 优先**

```
第一步：核心功能
👤 你：创建用户登录和注册

第二步：扩展功能
👤 你：添加商品浏览功能

第三步：交易功能
👤 你：添加购物车和订单

第四步：高级功能
👤 你：集成支付和物流
```

**策略 2: 功能分层**

```
Layer 1: 基础（必须）
├─ 用户认证
├─ 基础 CRUD
└─ 基本验证

Layer 2: 增强（重要）
├─ 高级查询
├─ 缓存优化
└─ 错误处理

Layer 3: 高级（可选）
├─ 数据分析
├─ 性能监控
└─ 自动化测试
```

**策略 3: 迭代开发**

```
迭代 1: 可工作的版本
└─ 最小功能集

迭代 2: 完善功能
└─ 添加边界处理

迭代 3: 优化提升
└─ 性能和用户体验
```

#### 实战案例

**场景**：创建博客系统

```
❌ 一次性要求：
👤 你：创建一个博客系统，包括文章管理、
    评论、标签、分类、搜索、推荐、SEO...

✅ 分步要求：

迭代 1：
👤 你：创建博客文章的 CRUD 功能
🤖 Claude：[实现基础功能]

👤 你：[审查测试]
✓ 功能正常

迭代 2：
👤 你：为文章添加评论功能
🤖 Claude：[扩展评论系统]

👤 你：[审查测试]
✓ 功能正常

迭代 3：
👤 你：添加标签和分类功能
🤖 Claude：[实现标签分类]

... 依此类推
```

### 错误 6: 忽视上下文 ❌

#### 症状

```
❌ 忽视上下文：
👤 你：创建一个 React 组件

🤖 Claude：[生成通用组件]

👤 你：但这不符合我的项目风格...
💥 需要大量修改
```

#### 问题分析

**上下文的重要性**

```
无上下文
    ↓
Claude 猜测
    ↓
生成通用代码
    ↓
可能不匹配：
├─ 代码风格
├─ 项目结构
├─ 技术栈版本
└─ 团队规范
```

**有上下文**
```
提供上下文
    ↓
Claude 理解
    ↓
生成定制代码
    ↓
完美匹配：
✓ 代码风格一致
✓ 结构匹配
✓ 版本兼容
✓ 符合规范
```

#### 上下文类型

**1. 项目上下文（CLAUDE.md）**

```markdown
# .claude/CLAUDE.md

## 项目概述
电商后台管理系统

## 技术栈
- React 18 + TypeScript
- TailwindCSS
- React Query

## 代码规范
- 组件命名：PascalCase
- 工具函数：camelCase
- 所有组件必须有类型定义
```

**2. 文件上下文（@ 符号）**

```
👤 你：@src/components/Button.tsx
    @src/components/Button.test.tsx
    为 Button 组件添加 loading 状态

🤖 Claude：
[读取现有代码]
[理解组件风格]
[添加符合风格的 loading 状态]
[更新测试]
```

**3. 历史上下文（会话）**

```
第一轮：
👤 你：创建用户登录组件
🤖 Claude：[创建组件]

第二轮：
👤 你：添加记住密码功能
🤖 Claude：[扩展现有组件]

✓ Claude 记得之前的上下文
✓ 保持代码风格一致
```

#### 上下文最佳实践

**实践 1: 创建 CLAUDE.md**

```markdown
✅ 必须包含：
- 项目概述
- 技术栈和版本
- 代码规范
- 目录结构
- 重要约定
```

**实践 2: 引用相关文件**

```
❌ 不引用：
👤 你：重构这个函数
[但 Claude 不知道函数在哪里]

✅ 引用：
👤 你：@src/utils/data.ts
    重构 process 函数
```

**实践 3: 说明关系**

```
❌ 孤立：
👤 你：创建用户注销功能

✅ 关联：
👤 你：@src/features/auth/
    在现有的认证系统中添加注销功能，
    复用已有的 API 客户端
```

### 错误 7: 不使用 CLAUDE.md ❌

#### 痊状

```
❌ 不使用 CLAUDE.md：
每次对话都要重复：
- "我的项目使用 React 18"
- "组件要放在 src/components/"
- "命名要用 PascalCase"
- "所有组件需要测试"

结果：浪费时间，容易遗漏信息
```

#### 问题分析

**CLAUDE.md 的价值**

```
每次对话
    ↓
重复说明项目信息（2-3分钟）
    ↓
30 次对话 = 60-90 分钟浪费

vs

创建 CLAUDE.md（10分钟）
    ↓
自动加载上下文
    ↓
节省时间，提高质量
```

#### CLAUDE.md 必备内容

**最小版本（5分钟）**

```markdown
# 项目说明

## 技术栈
React 18 + TypeScript + Vite

## 代码规范
- 组件：PascalCase
- 工具：camelCase
- 常量：UPPER_SNAKE_CASE
```

**推荐版本（10分钟）**

```markdown
# 项目说明

## 项目概述
[1-2 句话描述项目]

## 技术栈
- 前端：[框架和版本]
- 后端：[语言和框架]
- 数据库：[类型]

## 代码规范
- 命名约定
- 文件组织
- 注释要求

## 重要约定
- 不要修改的目录
- 特殊配置
- 测试要求
```

**完整版本（20分钟）**

```markdown
# 项目说明

## 项目概述
[详细描述]

## 技术栈
[完整列表和版本]

## 项目结构
[目录树和说明]

## 代码规范
[详细规范]

## 工作流程
[开发流程]

## API 规范
[接口标准]

## Git 工作流
[分支和提交规范]
```

#### 创建 CLAUDE.md 的技巧

```
👤 你：/init

👤 你：根据分析结果创建 CLAUDE.md

```


**技巧 3: 团队协作**

```
团队共同维护 CLAUDE.md
- 每个人添加自己了解的部分
- 定期评审和更新
- 确保信息准确
```

## 效率问题

### 错误 8: 重复说明背景 ❌

#### 症状

```
第一次对话：
👤 你：我的项目是一个电商系统，使用 React...
    创建商品列表组件

第二次对话：
👤 你：我的项目是一个电商系统，使用 React...
    添加购物车功能

第三次对话：
👤 你：我的项目是一个电商系统，使用 React...
    创建订单页面

... 重复说明浪费时间和 Token
```

#### 解决方案

**方案 1: 使用 CLAUDE.md**

```
创建 CLAUDE.md：
## 项目概述
电商系统，React 18 + TypeScript

之后不需要重复说明：
👤 你：创建商品列表组件
🤖 Claude：[已从 CLAUDE.md 了解项目]
```

**方案 2: 使用会话管理**

```bash
# 命名会话
claude --session ecommerce-project

# Claude 记得所有上下文
# 不需要重复说明
```

**方案 3: 引用已有文件**

```
第一次：
👤 你：创建商品管理 API
🤖 Claude：[创建 src/api/products.ts]

之后：
👤 你：@src/api/products.ts
    添加批量删除功能
🤖 Claude：[读取现有代码，理解上下文]
```

#### Token 优化

**避免重复的 Token 消耗**

```
❌ 每次都说明（每次 ~200 tokens）
30 次对话 = 6000 tokens 浪费

✅ 使用 CLAUDE.md（一次性 ~500 tokens）
30 次对话 = 500 tokens
节省：5500 tokens ≈ $0.01-0.05
```

### 错误 9: 不善用 Plan 模式 ❌

#### 症状

```
❌ 直接执行复杂任务：
👤 你：重构整个认证系统
🤖 Claude：[直接开始修改]
💥 改动了 20+ 个文件
💥 出错了，难以回滚
```

#### 何时使用 Plan 模式

```
✅ 必须使用：
- 大规模重构（5+ 文件）
- 架构调整
- 技术栈迁移
- 性能优化

❌ 不需要：
- 创建单个文件
- 简单 bug 修复
- 信息查询
```

#### Plan 模式的价值

**案例：数据库迁移**

```
❌ 不使用 Plan：
👤 你：将 MySQL 迁移到 PostgreSQL
🤖 Claude：[直接开始修改]
💥 修改过程中出错
💥 不知道改到哪一步了
💥 难以恢复

✅ 使用 Plan：
👤 你：[Shift+Tab] 将 MySQL 迁移到 PostgreSQL
🤖 Claude：
=== PLAN ===
1. 分析现有 schema
2. 转换 schema
3. 迁移数据
4. 更新连接配置
5. 更新查询代码
6. 测试验证
=== END PLAN ===

👤 你：审查计划，确认执行
🤖 Claude：[按计划执行]
✓ 清晰的进度
✓ 出错可以精确定位
```

#### Plan 模式最佳实践

**实践 1: 明确目标**

```
✅ 好：
"迁移到 PostgreSQL，保持数据完整性"

❌ 差：
"换数据库"
```

**实践 2: 要求详细步骤**

```
👤 你：给出每个步骤的：
- 具体操作
- 预期结果
- 验证方法
```

**实践 3: 设置检查点**

```
👤 你：在计划中设置检查点，
    每 3 个步骤暂停一次让我确认
```

### 错误 10: 忽视快捷键 ❌

#### 症状

```

- 鼠标操作终端

结果：效率降低 50%+
```

#### 必须掌握的快捷键

**Top 10 快捷键**

| 快捷键 | 功能 | 使用频率 | 节省时间 |
|--------|------|---------|---------|
| `@文件` | 引用文件 | ⭐⭐⭐⭐⭐ | 每次节省 30秒 |
| `!命令` | 执行命令 | ⭐⭐⭐⭐⭐ | 每次节省 20秒 |
| `Shift+Tab` | Plan 模式 | ⭐⭐⭐⭐ | 避免错误 |
| `Esc` | 撤销操作 | ⭐⭐⭐⭐ | 快速恢复 |
| `Ctrl+R` | 历史搜索 | ⭐⭐⭐ | 节省记忆 |
| `Ctrl+C` | 中断操作 | ⭐⭐⭐⭐⭐ | 紧急停止 |
| `Ctrl+D` | 退出会话 | ⭐⭐⭐⭐ | 快速退出 |
| `Tab` | 自动补全 | ⭐⭐⭐⭐ | 减少输入 |
| `↑/↓` | 历史命令 | ⭐⭐⭐⭐ | 复用命令 |
| `Ctrl+L` | 清屏 | ⭐⭐⭐ | 清理视图 |

**效率计算**

```
每天使用：
- @符号：20次 × 30秒 = 10分钟
- !命令：15次 × 20秒 = 5分钟
- Ctrl+R：5次 × 15秒 = 1.25分钟

每天节省：16.25分钟
每月节省：~8小时
```


**第 3 周：形成习惯**
