## Plan 模式概述

### 什么是 Plan 模式？

**定义**：Plan 模式让 Claude Code 在执行操作前先制定详细计划，你审查确认后再实施。

```
传统模式：
需求 → 直接执行 → 结果（可能不满意）

Plan 模式：
需求 → 制定计划 → 审查确认 → 执行实施 → 结果（符合预期）
```

### 为什么需要 Plan 模式？

#### 1. 避免灾难性操作

```
❌ 传统模式：
👤 你：重构这个项目的认证系统
🤖 Claude：[直接修改 20+ 个文件]
💥 破坏了现有功能，难以回滚

✅ Plan 模式：
👤 你：[Shift+Tab] 重构认证系统
🤖 Claude：[显示详细计划]
👤 你：[审查计划，发现风险点]
🤖 Claude：[调整计划，安全执行]
✓ 可控的变更
```

#### 2. 理解 AI 思路

```
Plan 模式的优势：
- 看到 Claude 的思考过程
- 理解操作顺序和依赖关系
- 发现潜在的遗漏
- 优化实施方案
```

#### 3. 提升效率

```
虽然看起来多了"规划"步骤，实际更高效：

传统模式：
执行 → 发现错误 → 修复 → 再发现 → 再修复...
（多次迭代）

Plan 模式：
规划 → 一次执行 → 成功
（一次完成）
```

## 核心概念

### Plan 模式的特点

#### 1. 分离关注点

```
规划阶段（Plan）
    ↓
关注：做什么、为什么、怎么做
    ↓
执行阶段（Execute）
    ↓
关注：具体实现
```

#### 2. 渐进式确认

```
第一步计划 → 确认 → 执行
    ↓
第二步计划 → 确认 → 执行
    ↓
第三步计划 → 确认 → 执行
```

#### 3. 可逆性

```
Plan 模式 = 可逆的操作

每个步骤都是：
- 明确的
- 可审查的
- 可撤销的
```

### Plan 模式 vs 直接模式

| 维度 | Plan 模式 | 直接模式 |
|------|----------|---------|
| **适用场景** | 复杂任务（5+文件） | 简单任务（1-2文件） |
| **安全性** | 高（先确认） | 中（直接执行） |
| **速度** | 慢（规划+执行） | 快（直接执行） |
| **控制力** | 高（逐步确认） | 低（一次性完成） |
| **Token 成本** | 略高（规划过程） | 较低 |
| **整体效率** | 高（减少错误） | 中（可能反复） |

```
              ↓
┌─────────────────────────────────────┐
│  3. 生成计划                         │
│     Claude：详细的步骤说明           │
│     - 目标                           │
│     - 步骤清单                       │
│     - 预期结果                       │
│     - 风险提示                       │
└─────────────────────────────────────┘
              ↓
┌─────────────────────────────────────┐
│  4. 审查计划                         │
│     你：检查计划的                   │
│     - 完整性                         │
│     - 合理性                         │
│     - 风险性                         │
└─────────────────────────────────────┘
              ↓
        ┌─────┴─────┐
        ↓           ↓
    [满意]      [需要调整]
        ↓           ↓

        ↓           ↓

    ↓           ↓

┌─────────────────────────────────────┐
│  6. 验证结果                         │
│     你：确认所有操作正确             │

```

### 计划的结构

一个完整的 Plan 模式计划通常包含：

```markdown
=== PLAN ===

## 目标
[明确的目标描述]

## 步骤
1. [步骤 1]
   - 操作：[具体操作]
   - 文件：[涉及的文件]
   - 预期：[预期结果]

2. [步骤 2]
   ...

## 风险提示
- [风险 1]
- [风险 2]

## 预计时间
[时间估算]

=== END PLAN ===

确认执行吗？(yes/no/modify)
```

## 实战案例

### 案例 1：大规模项目重构

**场景**：将 JavaScript 项目迁移到 TypeScript

```
👤 你：[Shift+Tab] 将这个 React 项目从 JavaScript 迁移到 TypeScript

🤖 Claude：
=== PLAN ===

目标：JavaScript → TypeScript 迁移

影响范围：
- 50+ 个组件文件
- 20+ 个工具文件
- 配置文件

步骤：
阶段 1：准备（步骤 1-3）
1. 安装 TypeScript 和类型定义
   !npm install --save-dev typescript @types/react @types/node
   预期：成功安装，无版本冲突

2. 初始化 tsconfig.json
   创建 tsconfig.json
   配置：严格模式、路径映射
   预期：符合项目需求

3. 更新构建脚本
   修改 package.json
   添加 tsc 构建命令
   预期：构建流程可用

【检查点】确认准备阶段完成？

阶段 2：类型迁移（步骤 4-6）
4. 迁移类型定义（types/）
   创建 *.d.ts 文件
   预期：核心类型定义完成

5. 迁移工具函数（utils/）
   重命名 .js → .ts
   添加类型注解
   预期：无类型错误

6. 迁移组件（components/）
   重命名 .jsx → .tsx
   添加 Props 类型
   预期：组件类型化

【检查点】确认迁移阶段完成？

阶段 3：验证（步骤 7-8）
7. 运行类型检查
   !npx tsc --noEmit
   预期：无类型错误

8. 更新测试
   修改测试文件
   运行测试
   预期：所有测试通过

风险提示：
- 某些第三方库可能缺少类型定义
- 隐式 any 可能被忽略
- 构建时间可能增加

预计时间：2-3小时

=== END PLAN ===

👤 你：yes，开始执行

🤖 Claude：
[执行阶段 1...]
✓ 步骤 1 完成
✓ 步骤 2 完成
✓ 步骤 3 完成

【检查点】阶段 1 完成，是否继续？
👤 你：yes

[执行阶段 2...]
...
```

**关键点**：
- 分阶段执行，每阶段后有检查点
- 详细的预期结果
- 明确的风险提示
- 合理的时间估算

### 案例 2：数据库迁移

**场景**：从 MySQL 迁移到 PostgreSQL

```
👤 你：[Shift+Tab] 将数据库从 MySQL 迁移到 PostgreSQL

🤖 Claude：
=== PLAN ===

目标：MySQL → PostgreSQL 迁移

数据安全：⚠️ 高风险操作

前置检查：
1. 备份现有数据
   !mysqldump -u user -p database > backup.sql
   确认：备份文件已创建

2. 分析 schema 差异
   MySQL 类型 → PostgreSQL 类型映射
   确认：所有类型可映射

步骤：
阶段 1：准备 PostgreSQL
1. 安装 PostgreSQL
2. 创建数据库和用户
3. 配置连接

【检查点】确认 PostgreSQL 可用？

阶段 2：Schema 转换
4. 转换表结构
   - AUTO_INCREMENT → SERIAL
   - TINYINT → SMALLINT
   - ENUM → VARCHAR + CHECK
5. 转换索引
6. 转换外键

【检查点】确认 schema 正确？

阶段 3：数据迁移
7. 导出 MySQL 数据
8. 转换数据格式
   - 日期格式
   - 布尔值
   - ENUM 值
9. 导入 PostgreSQL
10. 验证数据完整性

【检查点】确认数据一致？

阶段 4：应用切换
11. 更新数据库连接配置
12. 更新查询代码
13. 测试所有功能
14. 回滚方案准备

风险提示：
⚠️ 数据丢失风险
⚠️ 停机时间
⚠️ 应用兼容性

回滚计划：
如果步骤 13 测试失败：
1. 恢复 MySQL 连接
2. 从备份恢复数据
3. 分析失败原因

预计时间：4-6小时

=== END PLAN ===

👤 你：modify，步骤 1 添加验证备份文件完整性

🤖 Claude：
[更新计划]
1. 备份现有数据
   !mysqldump -u user -p database > backup.sql
   验证：检查 backup.sql 文件大小和完整性
   !test -f backup.sql && wc -l backup.sql
   确认：备份文件有效

=== END PLAN ===

👤 你：yes

🤖 Claude：[开始执行...]
```

**关键点**：
- 高风险操作，强调数据安全
- 详细的回滚计划
- 分阶段验证
- 风险提示醒目

## 常见问题

### Q1: Plan 模式会增加多少成本？

**A**: 通常增加 20-30% 的 Token 使用，但能避免更昂贵的错误。

```
成本对比：

直接模式：
执行 → 出错 → 修复 → 再出错 → 再修复...
总 Token：高（多次尝试）

Plan 模式：
规划 → 一次执行成功
总 Token：中（一次成功）

结论：Plan 模式更经济
```

### Q2: 可以在执行中修改计划吗？

**A**: 可以，随时可以：

```
👤 你：暂停，修改下一步的计划

🤖 Claude：
当前已完成：步骤 1-3
下一步：步骤 4

待修改的步骤：
4. [原计划]

修改为：
4. [新计划]

继续执行吗？
```

### Q3: Plan 模式失败怎么办？

**A**: Plan 模式本身不会失败，但计划可能不完美：

```
如果执行中发现问题：
1. 暂停执行
2. 分析问题原因
3. 调整剩余计划
4. 继续执行
```

### Q4: 小任务也需要 Plan 模式吗？

**A**: 不需要，但可以：

```
小任务（1-2个文件）：
- 直接执行更快
- Plan 模式反而浪费时间

中任务（3-5个文件）：
- 看情况
- 不熟悉则用 Plan

大任务（5+个文件）：
- 必须用 Plan 模式
```

### Q5: 计划可以保存吗？

**A**: 可以，要求 Claude 保存：

```
👤 你：将这个计划保存为 plan.md

🤖 Claude：[创建 plan.md 文件]

下次使用：
👤 你：@plan.md 按照这个计划执行
```
